2. Request / control flow (a typical authenticated call)

sequenceDiagram
    actor U as User (Browser)
    participant FE as React App
    participant AX as axios (adds JWT)
    participant MW as Express Middleware Chain
    participant RT as Route Handler
    participant DB as MongoDB

    U->>FE: Clicks a button (e.g. "Send email")
    FE->>AX: api.post("/outreach/send", data)
    AX->>MW: HTTPS request + Authorization: Bearer JWT
    MW->>MW: morgan logs the raw request line
    MW->>MW: activityLogger wraps res.json() to capture the outcome later
    MW->>MW: helmet, mongoSanitize, cors, express.json()
    MW->>RT: protect() verifies JWT, attaches req.user
    RT->>RT: authorize("admin","service") checks role
    RT->>DB: Mongoose query / write
    DB-->>RT: result
    RT-->>MW: res.json(...)
    MW->>MW: "finish" event — activityLogger logs "who did what" to stdout and Mongo
    MW-->>AX: JSON response
    AX-->>FE: resolved promise
    FE->>U: ToastContext shows a success/error toast

Two logging layers run on every request, independently: morgan (raw HTTP line → stdout only) and activityLogger (human-readable "who did what" → stdout and the ActivityLog collection, visible in the admin Activity tab). Read-only GETs are skipped.

Pricing, Portfolio, and CompanyInfo are standalone content collections (admin-editable, no user references) — they feed the public site, Givi's chatbot context, and the AI Lead Finder's outreach/proposal generation via one shared buildServiceContext() helper. Otp/PasswordReset are ephemeral (TTL-expired). SecurityEvent (90-day TTL) and BlockedIP are IP-keyed, not user-keyed — the USER link is optional/best-effort. BizLead reuses the existing Outreach collection as its communication history (an optional lead ref was added rather than a second email log).

5. Phone OTP verification + registration flow

sequenceDiagram
    actor V as Visitor
    participant FE as Register Page
    participant API as Backend
    participant Twilio
    participant DB as MongoDB (Otp)

    V->>FE: Enters phone number
    FE->>API: POST /api/auth/send-otp
    API->>DB: store hashed 6-digit code (5 min TTL)
    API->>Twilio: send SMS
    alt Twilio succeeds
        Twilio-->>V: SMS with code
    else Twilio fails / not configured
        API-->>FE: devCode returned directly (dev fallback only)
    end
    V->>FE: types code into OtpBoxes (auto-advance + paste support)
    FE->>API: POST /api/auth/verify-otp
    API->>DB: compare hash, mark verified (15 min window)
    API-->>FE: verified: true
    FE->>FE: animated checkmark reveal ("Verified!")
    V->>FE: completes name / email / password
    FE->>API: POST /api/auth/register (or register-admin / register-service)
    API->>DB: create User, delete the spent Otp
    API-->>FE: JWT + user
    FE->>FE: store token, redirect to the role's dashboard

Every email/phone input site-wide now also gets live client-side format validation — a red warning icon while invalid, a green check once it matches (ValidatedInput.jsx + utils/validators.js, the phone regex mirroring the backend's own normalizePhone). UX feedback only; the backend independently re-validates on every write.

6. Payment → Invoice → Refund flow

sequenceDiagram
    actor C as Client
    participant FE as Client Dashboard
    participant API as paymentRoutes.js
    participant RZP as Razorpay
    participant DB as MongoDB (Order)
    participant Mail as sendEmail

    C->>FE: Requests a project (service + custom amount)
    FE->>API: POST /payments/create-order
    API->>API: Enforce price floor — amount >= basePrice - 5000
    API->>RZP: orders.create()
    RZP-->>API: razorpay order id
    API->>DB: Order paymentStatus: "unpaid"
    C->>RZP: Completes checkout (Razorpay widget)
    FE->>API: POST /payments/verify (signature)
    API->>DB: Order paymentStatus: "paid"
    API-->>Mail: payment confirmation email

    Note over C,DB: Self-cancellation window — 48h from request
    C->>FE: Cancel project
    FE->>API: PATCH /payments/orders/:id/cancel
    alt order is paid
        API->>RZP: payments.refund(paymentId, amount)
        alt refund succeeds
            RZP-->>API: refund id
            API->>DB: paymentStatus: "refunded", refundId, refundedAt
            API-->>Mail: refund confirmation email
        else refund API call fails
            API-->>FE: 502 — order left COMPLETELY unchanged
        end
    else order was never paid
        API->>DB: status: "cancelled"
    end

    C->>FE: Download invoice / payment details
    FE->>API: GET /payments/orders/:id/invoice (blob, JWT header)
    API->>API: generateInvoicePdf() — PDFKit, streamed directly
    API-->>FE: application/pdf

Fail-safe by design: a failed Razorpay refund call never marks the order "cancelled"/"refunded" — it leaves the order's state completely untouched and returns a clear error, rather than silently promising a refund that didn't happen. The invoice includes a refund note when applicable. PDFKit's standard fonts have no ₹ glyph, so amounts render as Rs. 25,000 — a font limitation, not a bug. The frontend download uses responseType:"blob" + createObjectURL since a plain <a href> can't carry the Authorization header a protected route needs.

Key architectural decisions worth remembering

  • Security enforced server-side only. ProtectedRoute on the frontend is UX convenience; every backend route independently re-verifies the JWT and role via protect/authorize.
  • AI features are grounded, not freeform. Givi (chat), Service Dashboard outreach drafts, and the AI Lead Finder's email/proposal generation all pull live data from MongoDB via one shared buildServiceContext() helper, rather than letting the model invent facts or three copies of "what services do we offer" drift apart.
  • Two independent logging layers. morgan (raw HTTP) and activityLogger (semantic audit trail) are separate, composable middleware.
  • Security controls are detection-driven, not just preventive. Rate limits, brute-force lockout, and content screening all feed one SecurityEvent log; registerViolation() correlates violations across endpoints per IP (a bad login + a flagged chat message count toward the same auto-block threshold), not just per-route.
  • Fail-safe over fail-silent for money. See §6 — a failed refund never leaves the system in a state that implies success.
  • Price floor enforced where the money moves, not just the UI. The request-project form mirrors the ₹5,000-below-basePrice floor for UX, but create-order re-derives and enforces it server-side independently.
  • New data-gathering features are scoped to what's actually legal to automate. The AI Business Lead Finder discovers businesses via Google's official, ToS-compliant Places API rather than scraping Maps/Justdial; the New Business Monitor is CSV-import/manual-entry only, since India's MCA registry has no free bulk API. Both constraints are surfaced directly in the admin UI's own copy.
  • Theme system is CSS-variable-driven. Almost everything adapts to light/dark automatically. Only real WebGL/Canvas scenes need an explicit per-theme JS color palette.
